# Security policy

## Reporting a vulnerability

Report suspected vulnerabilities privately through GitHub private vulnerability
reporting on this repository:

<https://github.com/bitcoinuniverseio/op-drop/security/advisories/new>

Do not open a public issue, a pull request, or a discussion for a security problem.
A public report gives everyone the exploit at the same time you give it to us.

### What helps

- What you did, what you expected, and what happened.
- The affected page, document, rule identifier (for example `OD-4.8`), or code path.
- A leaf script hex, payload, or transaction id that reproduces it, where one exists.
- Whether the issue is in the specification itself, in this site's client-side tool,
  or in an implementation.

### What never belongs in a report

Private keys, seed phrases, wallet files, mnemonic phrases, API tokens, or anyone's
personal data. If reproducing an issue seems to require a secret, say so and we will
find another way.

### What to expect

We aim to acknowledge a report within a few working days, tell you whether we can
reproduce it, and agree a disclosure timeline with you. Please give us a reasonable
window to fix a confirmed issue before publishing.

## Scope

| In scope | Out of scope |
| --- | --- |
| Errors in the published specification that would cause two correct implementations to disagree | Bitcoin Core, Taproot, or any Bitcoin consensus rule |
| A test vector whose stated outcome is wrong | Third-party wallets, explorers, or indexers, none of which support OP_DROP |
| A defect in the client-side builder and decoder on this site | The price, availability, or market behaviour of any token |
| Documentation that overstates support, safety, or guarantees | Feature requests and design disagreements: open an issue for those |
| A missing safety warning where a user could lose funds by following our instructions | Reports generated by an automated scanner with no demonstrated impact |

## Things worth knowing before you report

Several properties look like vulnerabilities and are documented, intended behaviour.
They are listed in full under
[security considerations](https://bitcoinuniverseio.github.io/op-drop/reference.html#security).
The most commonly reported are:

- **A payload is permanent and public** once the reveal confirms.
- **Deploys can be front-run.** Tickers are unreserved and decided by chain order.
- **A failed event still costs the fee.** Losing a mint race produces a confirmed
  transaction that changes nothing.
- **Output 0 is the settlement destination.** If a wallet places change first, the
  change address receives the transferred units.
- **Anchor control is settlement control.** Whoever can spend the anchor decides
  where a transfer lands.
- **A reorg can retract a confirmed event.** Depth matters.

If you believe one of these is worse than documented, that is a valid report. Tell us
which one and why.

## Supported versions

The specification version is 1.0.0 and the lifecycle is experimental. Only the current
published version is supported. Security-relevant corrections are recorded in the
[changelog](https://bitcoinuniverseio.github.io/op-drop/changelog.html).
